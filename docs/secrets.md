# Secrets

What secrets exist in this fleet, where they live, and how to handle
them safely.

## Inventory of secrets

| Secret | Where it lives | How it's generated |
|--------|----------------|--------------------|
| LUKS swap keyfile | `/etc/fstab.swap_keyfile` (mode 0400, root) | `xkcdpass -n 25` during bootstrap.sh |
| LUKS /boot keyfile | `/etc/fstab.boot_keyfile` (mode 0400, root) | `xkcdpass -n 25` during bootstrap.sh |
| LUKS /boot passphrase | typed at GRUB | set by user during bootstrap.sh's `luksAddKey` |
| ZFS pool key | `/etc/fstab.zfs_keyfile` (mode 0400, root) | `xkcdpass -n 25` during bootstrap.sh |
| ZFS initramfs alias | `/crypto_keyfile.bin` → ^ | symlink, baked into initramfs by mkinitfs |
| Secure Boot CA private key | `/boot/secureboot/sb.key` (mode 0600, root) | `community.crypto.openssl_privatekey` |
| Secure Boot CA cert | `/boot/secureboot/sb.crt` + `sb.cer` (DER) | `community.crypto.x509_certificate` |
| WireGuard server private key | `/etc/wireguard/<iface>.key` (mode 0600, root) | `wg genkey` (idempotent — never re-rolled) |
| WireGuard peer pubkeys | inventory group_vars | generated by each peer; pasted into vars |
| Grafana admin password | `/etc/grafana.ini` | `grafana_admin_password` var (defaults to `admin`!) |
| SSH host keys | `/etc/ssh/ssh_host_*` | generated by sshd on first start |
| SSH authorized_keys | `/root/.ssh/authorized_keys` | dropped by bootstrap.sh; you append for ansible |
| Docker swarm join tokens | runtime-only | read via `docker_swarm_info` per play |

## Defense-in-depth model

The threat model assumes:

1. **Physical access to a powered-off bare-metal box** is contained
   by:
   - Full-disk encryption (ZFS) — keyfile is on the encrypted root;
     attacker needs the boot LUKS passphrase to read kernel/initramfs
     containing the key.
   - LUKS /boot — encrypted with both a keyfile (stored on encrypted
     ZFS root, only useful at runtime) and a passphrase (typed at
     GRUB). Attacker without the passphrase can't even read the
     bootloader's kernel.
   - Secure Boot — kernel + bootloader signed with a self-signed CA
     enrolled in firmware. Attacker can't substitute a malicious
     kernel that exfiltrates the LUKS passphrase.

2. **A compromised internet-facing host (wireguard hub)** is
   contained by:
   - The hub knows peer pubkeys, not privkeys. Compromising the hub
     gives the attacker the ability to MITM peer traffic via the
     hub, but not to decrypt past traffic.
   - Hub doesn't have ssh keys for other fleet hosts in its filesystem
     — the management plane is the wireguard tunnel + ansible's
     control node, neither of which lives on the hub.

3. **Compromised observability host** is contained by: it has read-
   only scrape access to other hosts' /metrics endpoints (no
   credentials needed; metrics are public over wg). It can read
   logs that have already been pushed to it. It has no ssh keys for
   other hosts.

What's *not* in the threat model:

- Hardware key extraction from a powered-on, logged-in box (TPM,
  cold-boot attacks). These are mitigated by physical security.
- A compromised ansible control node. Whoever runs ansible has full
  fleet access; treat the control node accordingly.

## Vault: when to use it

Ansible Vault encrypts strings or whole files at rest in the repo.
Use it for any value you wouldn't paste into a public gist.

### Vault candidates in this repo

- `grafana_admin_password` — high priority, currently `admin`.
- `wireguard_peers[].preshared_key` — if you're using PSKs.
- `cdn_edge_bgp_peers[].password` — MD5 BGP auth.
- TLS private keys, if you ever store them in inventory rather than
  fetching at deploy time.

### Setup

```sh
ansible-vault create inventory/group_vars/observability.vault.yml
# Edit, save. File on disk is encrypted.
```

In the file:
```yaml
grafana_admin_password: "your-actual-strong-password"
```

To decrypt for editing: `ansible-vault edit ...`. To run plays:
`ansible-playbook ... --ask-vault-pass` (or use a vault password
file).

### Vault password file

Store your vault password in `~/.config/ansible/vault.txt` (mode 0600),
add to `ansible.cfg`:
```ini
[defaults]
vault_password_file = ~/.config/ansible/vault.txt
```

Never check the password file into the repo.

## Keyfile rotation

### Rotate the ZFS pool key

```sh
zfs change-key -l \
    -o keylocation=prompt \
    -o keyformat=passphrase \
    rpool
# enter old passphrase, then new
```

After this, generate a new keyfile and re-point:

```sh
xkcdpass -n 25 > /etc/fstab.zfs_keyfile
chmod 0400 /etc/fstab.zfs_keyfile
zfs change-key -l \
    -o keyformat=passphrase \
    -o keylocation=file:///crypto_keyfile.bin \
    rpool < /etc/fstab.zfs_keyfile
mkinitfs $(ls /lib/modules)
```

### Rotate the boot LUKS passphrase

```sh
cryptsetup luksAddKey /dev/nvme0n1p2     # adds new slot
# enter existing passphrase or use keyfile, then new one
cryptsetup luksKillSlot /dev/nvme0n1p2 N  # kill old slot N
cryptsetup luksDump /dev/nvme0n1p2        # confirm slot table
```

### Rotate the WireGuard server key

```sh
# On the hub:
rm /etc/wireguard/wg0.{key,pub}
ansible-playbook ... playbooks/wireguard.yml -l hub
# Note new pubkey from the play output.
# Update every peer's config to point at the new pubkey.
```

There's no in-place rotation — peers will lose connectivity until
their configs are updated. Plan accordingly.

### Rotate Secure Boot CA

Out of scope for routine rotation. If the key is suspected
compromised:

1. Generate a new CA + cert; sign current bootloader/kernel with
   both old and new (sbsign supports multi-sig).
2. Add the new cert to firmware as KEK/db.
3. Verify boot works.
4. Remove the old cert from firmware.
5. Re-sign with only the new cert.
6. Wipe the old key.

## Backup story

Two files are *unconditionally* needed to recover a bare-metal host:

- `/etc/fstab.zfs_keyfile`
- `/etc/fstab.boot_keyfile` (or remember the boot LUKS passphrase)

Lose both and the disk is unrecoverable.

The original alpine.sh (from wejn.org, which our bootstrap is based
on) has an optional step that GPG-encrypts these to your public key
and drops the .asc files on the ESP. **bootstrap.sh doesn't do this
by default** — add it manually if you want it. The recipe:

```sh
# After bootstrap.sh, on the new system:
gpg --import your-recovery-key.asc
echo 'YOUR-GPG-KEY-ID:6:' | gpg --import-ownertrust

for f in /etc/fstab.*_keyfile /boot/secureboot/sb.{key,crt}; do
    gpg --encrypt -r your-recovery-key --armor < $f \
        > /efi/$(basename $f).asc
done
```

Now the ESP has GPG-encrypted copies of every keyfile. From any
machine with your GPG key, you can decrypt them.

## Per-host secrets in vault

If a single host has truly per-host secrets (e.g. an API token):

```sh
ansible-vault create inventory/host_vars/edge1.vault.yml
```

```yaml
acme_account_key: |
  -----BEGIN PRIVATE KEY-----
  ...
  -----END PRIVATE KEY-----
```

Reference normally in role vars: `{{ acme_account_key }}`. Ansible
auto-loads `host_vars/edge1.yml` AND `host_vars/edge1.vault.yml`;
the vault one is decrypted on the fly.

## Things to never do

- **Don't commit unencrypted secrets** to inventory/. Use vault.
- **Don't log secrets** — use `no_log: true` on tasks that handle
  secrets (the wireguard_hub role's privkey-slurp task does this).
- **Don't bake secrets into bootstrap.sh** — pass via env vars or a
  file copied in alongside.
- **Don't share keyfiles across hosts.** Each host generates its own
  during bootstrap.sh.
- **Don't use the same Grafana admin password as your real admin
  password.** It's stored in the role's defaults until you vault it.
